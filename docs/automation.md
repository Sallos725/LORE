# 자동 기억 설정

PocketRisu 수정·재빌드 없이 Lite 플러그인 또는 Full 플러그인과 HTTP(S) 사이드카를 설치한다. 대화 모델과 기억 추출 모델은 독립적이다.

## 시작하기

1. PocketRisu에 로그인하고 사용할 채팅을 연다.
2. **채팅 메뉴 → LORE Lite/Full**을 연다. 전체 설정에서 채팅을 선택하지 않은 상태라면 먼저 채팅 화면으로 돌아온다.
3. Lite는 **현재 채팅 위키 열기**, Full은 사이드카 URL 입력 후 **연결**을 누른다. 별도 scope token, 캐릭터 ID, 채팅 ID 입력은 없다.
4. 자동 기억 설정에서 공급자·API 주소·모델·키를 지정한다. OpenAI/OpenRouter/Anthropic/Gemini/Ollama/사용자 지정 OpenAI 호환을 지원한다. Gemini는 `/v1beta` 기본 주소, 그 외에는 표시된 전체 API 주소를 사용한다. JSON 응답 모드는 지원 모델에서만 켠다.
5. **자동 기억 시작**을 누르고 PocketRisu의 플러그인 권한을 허용한다. 호스트는 예산 조회 권한을 “전체 데이터베이스”로 표시하지만 LORE는 `maxContext`, `maxResponse` 두 숫자만 요청한다. 전체 DB·캐릭터를 복사하지 않는다.
6. 창을 닫고 대화한다. 설정 URL·모델·예산은 다음에 다시 열어도 유지된다. 탭을 새로 열면 자동 기억을 다시 시작한다.

Lite API 키는 메모리에만 둔다. Full의 모델과 키는 서버의 private SQLite 데이터 볼륨에 저장하고 API 응답에는 키를 반환하지 않는다. Full 재시작 뒤에도 이미 수락한 작업이 계속된다. Full에서 마지막으로 지정한 추출 설정은 같은 설치의 새 채팅 기본값으로 사용하며, 각 채팅에서 설정을 바꿀 수 있다. 서버 환경 변수의 기본 모델도 지원한다.

## 봇 카드와 채팅별 위키

위키의 구분은 `설치 / 사용자 / 캐릭터 ID / 채팅 ID / 분기 ID`다. 같은 봇 카드의 채팅 A, B는 각각 다른 문서 군집·원문·이력·작업을 가진다. 채팅 전환 때 해당 위키로 전환하며, 같은 배열 위치에 새 채팅이 생겨도 ID가 다르면 새 위키다. 기존 채팅으로 돌아오면 이전 문서를 다시 사용한다. 분기의 원본 문서를 자동 복제하거나 기억을 합치지 않는다.

Lite의 노트북 이름은 비워 두면 위 안정 ID를 해시한 키로 자동 생성한다. 이전 버전의 수동 노트북이나 복원용 빈 노트북만 직접 이름으로 연다. Full은 로그인한 PocketRisu의 저장 채팅에서 범위를 확인한다. 설치 ID는 서버 볼륨에 유지하므로 볼륨을 복원하면 같은 범위를 쓴다. `LORE_POCKETRISU_URL`을 다른 origin으로 바꾸면 별도 설치로 취급한다.

## Full 연결

사이드카의 `.env`에 기존 PocketRisu origin을 지정한다.

```dotenv
LORE_POCKETRISU_URL=http://pocketrisu:6001
LORE_BIND_ADDRESS=127.0.0.1
LORE_PORT=6011
```

주소는 사이드카에서 접근 가능한 주소다. 컨테이너의 localhost는 그 컨테이너 자신이다. 같은 Docker 네트워크의 서비스 이름 또는 서버 내부망 주소를 사용한다. 기본 Compose는 내부 포트만 열고, `docker-compose.http.yml`을 함께 사용하면 지정한 인터페이스에 포트를 연결한다. 기존 PocketRisu·상위 Compose를 수정하지 않는다.

플러그인은 PocketRisu의 기존 HttpOnly 로그인 쿠키로 짧은 JWT를 자동 발급받는다. 사이드카는 고정된 PocketRisu origin에서 이 로그인을 검증한다. 토큰 생성·복사·입력은 없으며 JWT를 DB나 작업에 저장하지 않는다. 비밀번호가 설정되지 않은 호스트는 로그인 인증을 할 수 없으므로 먼저 PocketRisu 비밀번호를 설정한다. 자체 운영 사이드카를 사용하고 외부 인터넷 연결은 HTTPS로 구성한다.

## 원문과 주입

- 원본 PocketRisu V3의 캐릭터 getter는 숫자 인덱스를 반환한다. 기존 `/api/db/stats/characters`의 제한된 메타데이터로 안정 `chaId`를 찾고 `/api/chat-content/:chaId/:index`에서 실제 `chat.id`를 확인한다. 메타데이터 응답은 최대 256 KiB이며 전체 캐릭터 카드·대화 본문을 포함하지 않는다. 이 API는 서버에서 저장 DB를 읽으므로 작업 비용이 데이터 규모에 비례한다.
- `beforeRequest`의 user/assistant `memo`를 저장 원문의 `message.chatId`와 대조한다. 이번 사용자 입력을 제외한 최근 32개 anchor까지 수집하며, 아직 저장되지 않았거나 다른 분기의 anchor면 주입을 건너뛴다. 프롬프트·MARP 분석·생성 중 출력은 원문으로 저장하지 않는다.
- Full 원문은 서버에서만 읽으며 저장 채팅 16 MiB가 상한이다. 한 요청에서 최대 8×32 위치를 재조정한다. Lite는 저장 채팅 1 MiB·128개 메시지가 상한이다. 넘치는 원문을 조용히 잘라내지 않는다.
- 수정·삭제·재생성·되돌림은 다음 수집의 prefix hash 차이로 감지한다. 예전 근거 문서를 주입에서 제외하고 재수집한다. 늦은 LLM 결과가 새 원문이나 수동 교정을 덮어쓰지 않는다.
- 기본 **공통 요청 훅**은 공급자 변환 전 텍스트 프롬프트에 기억을 넣는다. 모델 프리셋도 이 훅을 거친다. 실제 원본 호스트의 Gemini 요청에서 주입을 검증한다. 이미지·도구 요청은 예산을 검증할 수 없어 건너뛴다.
- 선택 가능한 **최종 body 검사**는 기존 OpenAI `openai_basic`/`openai_streaming` 텍스트 요청 전용이다. 원문·범위·cursor와 최종 body의 응답 예약량을 다시 검사한다. 해당 훅을 거치지 않는 모델 프리셋에는 공통 훅을 사용한다.
- 예산은 UTF-8 기반 보수적 추정이다. 기존 API에 tokenizer가 없으므로 정확한 토큰 수는 보장하지 않는다. 공통 훅 이후의 다른 플러그인·트리거·공급자 변환은 검사 이후 변경이다. 필수 기억이나 전체 예산 초과 시 주입을 건너뛰고 이유를 표시한다.
- 단계별 기억 조회는 2.5초 뒤 일반 채팅으로 복귀한다. 늦은 완료가 성공 상태로 바뀌지 않으며, 종료하지 않은 RPC를 계속 중첩하지 않는다. 추출은 별도 비동기 작업으로 최대 3회 시도한다.

검색은 현재 질문과 최근 두 메시지의 일부를 합쳐 최대 200자로 수행한다. 이름이 생략된 후속 질문에 최근 인물·장소를 활용하며 다른 채팅의 문서는 검색하지 않는다.

새 답변은 다음 생성 요청에서 수집한다. 탭 종료 전에 보내지 못한 새 원문까지 자동 처리하는 서버 outbox는 없다. 서버가 수락한 작업의 지속과 새 대화 발견을 구분한다. 모바일 실기기와 장기 서사 품질의 검증 범위는 [공개 준비도](public-readiness.md)에 기록한다.
